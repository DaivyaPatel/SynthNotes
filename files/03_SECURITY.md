# Security & Data Handling — SynthNotes

Scoped for a mini-project handling user-uploaded documents and calling LLM APIs. This is not enterprise-grade hardening — it's the baseline a reviewer/mentor will reasonably expect, and what protects you if the project is later deployed beyond a local demo.

## 1. Secrets Management

- **Never commit API keys** (Gemini/Claude/any LLM provider) to the repository, in code, in tickets, or in the frontend prompt file
- Store all keys in a `.env` file at the project root; add `.env` to `.gitignore` from commit #1
- Provide a `.env.example` with variable names but no values, so Antigravity/any collaborator knows what to configure
- Load secrets via `python-dotenv` (backend) — never hardcode in `generate.py` or any pipeline module
- If using Antigravity's built-in model access (rather than raw API keys), confirm whether Antigravity injects credentials at runtime vs. requiring them in project config — do not duplicate keys in both places

## 2. File Upload Security

- **Validate file type by content, not just extension** — a `.txt` renamed from an executable should not be trusted on extension alone; check MIME type server-side
- **Enforce a maximum file size** per upload (e.g., 10–20 MB) to prevent resource-exhaustion via oversized PDFs
- **Enforce a maximum number of files per session** to bound pipeline cost/latency
- Store uploaded files outside any web-servable static directory — never let an uploaded file become directly fetchable by URL
- Sanitize filenames before writing to disk (strip path traversal characters — no `../` in stored filenames)
- Do not execute or `eval()` any content extracted from uploaded files

## 3. Data Privacy

- Uploaded documents may contain a student's personal course material — treat session data as private by default; no cross-session data sharing
- Set a **data retention policy** even for a demo project: define whether uploaded files/session outputs are deleted after N days or on session end, and implement at least a manual cleanup script
- If any analytics/logging is added, do not log full document text — log metadata only (file count, sizes, timing, error codes)

## 4. LLM API Usage

- Treat all extracted document text as **untrusted input** when constructing prompts sent to the Generation/Quiz LLM stage — a malicious or corrupted document should not be able to inject instructions that override the system prompt (prompt injection). Mitigate by:
  - Clearly delimiting source content from instructions in the prompt template (e.g., fenced blocks with explicit labels)
  - Never letting extracted document text be interpreted as system-level instructions
- Rate-limit or cap LLM calls per session to control cost and prevent runaway loops (e.g., a retry bug calling the API in an infinite loop)
- Log LLM call failures distinctly from pipeline failures, so cost/error issues are diagnosable

## 5. Backend/API Security

- Enable CORS only for the known frontend origin (`localhost:5173` in dev; the actual deployed origin in any later deployment) — do not leave it wildcard-open once beyond local dev
- Validate all API inputs server-side (file types, session IDs, config parameters) — do not trust frontend-side validation alone
- Return generic error messages to the client for unexpected failures; keep stack traces in server-side logs only, not in API responses

## 6. Dependency Hygiene

- Pin dependency versions (see Tech Stack doc) and periodically check for known CVEs in key packages (`transformers`, `torch`, `fastapi`) before submission/demo
- Avoid installing packages from unverified sources; stick to PyPI/npm official registries

## 7. Academic Integrity Note

- This is a project submitted for credit/marks — ensure any code, prompts, or scaffolding generated by Antigravity/Gemini/Claude is understood and explainable by the team; do not include unmodified third-party copyrighted material (e.g., textbook excerpts) in any submitted sample outputs beyond what's needed to demonstrate the pipeline on your own test sources
- Clearly attribute any external libraries, pretrained models, and reference papers in the final report/references slide

## 8. Out of Scope for This Version

- User authentication/authorization (single-user/local-demo assumption for v1) — flag explicitly if the frontend or deployment plan changes to multi-user, since that would require adding auth, per-user data isolation, and session tokens before it's safe to ship
- Encryption at rest for stored files (acceptable for local/demo scope; revisit if deployed with real user data)
